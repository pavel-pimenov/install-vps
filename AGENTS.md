# AGENTS.md

Памятка для LLM/агентов, работающих в этом репозитории.

## Проект

Асинхронная утилита `install-vps`: стартовая настройка новой Ubuntu-VPS
(24.04 / 26.04) по SSH-ключу. Работает без внешних Python-зависимостей:
вся связь — локальным системным `ssh`, удалённые действия — одиночным
стримовым bash-скриптом, передаваемым через stdin.

## ЖЁСТКОЕ ПРАВИЛО: всё исполняется только на удалённом хосте

Локальный узел — macOS-ноутбук разработчика. Это **редактор и ssh-клиент,
а не полигон**. Ничего, что относится к целевому хосту, на нём не
запускается.

- **Локально можно**: запускать сам `install-vps` / `python3 -m install_vps`
  (он локально только собирает текст скрипта и отдаёт его в
  `ssh … bash -s`), читать и править файлы репозитория, git, а также
  статические проверки кода `sh scripts/check.sh` (ruff / compileall /
  unittest) — они не поднимают служб, не лезут в сеть и не трогают систему.
- **Локально ЗАПРЕЩЕНО**: docker и colima, любые контейнеры; локальные
  веб-серверы и реверс-прокси (caddy, nginx); запуск любых чужих бинарников
  (caddy из GitHub-релизов, beszel, bandwhich, lazydocker); `pip install`,
  `brew`, любые изменения системы; «живые прогоны» собранных bash-скриптов,
  Caddyfile, compose-файлов и мок-сервисов; временные каталоги с файлами,
  которые должны жить на хосте.
- **Проверки целевого хоста — на хосте.** Caddyfile/compose валидируются
  его же контейнером: `docker exec caddy caddy validate --config
  /etc/caddy/Caddyfile` и `docker exec caddy caddy reload --config
  /etc/caddy/Caddyfile`; `bash -n` удалённого скрипта и `curl` по хосту.
  Не поднимать «вместо хоста» локальный caddy с моками — прошлый опыт
  показал, что такие прогоны всё равно не ловят главного, зато трогают
  ноутбук.
- **Если задача не выполнима без локального запуска чего-либо — спросить
  пользователя**, а не молча запускать. Обход правила не изобретать:
  ни колбы в `/tmp` ноутбука, ни «одноразовый» caddy в Colima.

## Рабочие команды (обязательно перед сдачей)

```bash
sh scripts/check.sh                 # ruff + compileall + тесты (быстрее всего)
python3 -m ruff check install_vps tests
python3 -m compileall -q install_vps
python3 -m unittest discover -s tests
python3 -m install_vps <host>        # реальный прогон (или --verify-only)
ssh <host> 'docker exec caddy caddy validate --config /etc/caddy/Caddyfile'
```

Все должно проходить чисто (ruff: 0 ошибок, тесты: OK). Кодировка исходников —
UTF-8, длина строки в python-коде — 120 (`line-length` в `pyproject.toml`),
в bash-шаблонах — свободно. ВЕРсия: `install_vps/__init__.py:__version__`
(в `pyproject.toml` она динамическая) + запись в `HISTORY.md`.

Тесты в `tests/test_install_vps.py` гоняют `bash -n` по собранному скрипту —
это ловит незакрытые `if`/кавычки/heredoc в шаблонах, которые иначе видны
только на боевом хосте. Caddyfile/`redir`/`handle` проверяются на хосте его же
контейнером: у `redir` первый позиционный аргумент — матчер, поэтому
редирект на слэш пишется как `redir * /путь/ 308`, иначе он молча ничего
не делает и запрос без слэша уходит в catch-all.

## Как устроен код

- `install_vps/cli.py` — разбор CLI, слияние `config.toml` + флаги,
  точка входа `main()`.
- `install_vps/config.py` — `Config` (dataclass) и загрузка TOML
  (стандартный `tomllib`, без парс-зависимостей).
- `install_vps/ssh.py` — `RemoteHost`: собирает системную команду
  `ssh -p PORT -i KEY [-o ...] USER@HOST`, потоково запускает удалённый
  скрипт через `bash -s` (stdin), стримит вывод в консоль.
- `install_vps/installer.py` — bash-шаблоны (строки с `.format()`),
  генераторы сайтов/страниц/утилит на Python, `install()` и `verify()`.
  Валидация конфига — в `_validate()`, она обязана срабатывать **до**
  похода в SSH: генераторы прогоняются для проверки того, что уйдёт на хост.
- Утилиты вне репозиториев Ubuntu (`_GITHUB_TOOLS`): версия, имя файла и
  sha256 архива **и** бинарника закреплены в коде. Версию/хеши менять
  только после пересчёта по реальным файлам релиза.

## Правила доработок

1. **Аккуратно с sudo/root**: скрипт сам определяет на хосте, root ли
   пользователь; при не-root требует `sudo -n` (NOPASSWD) и падает с
   понятной ошибкой. Не вводить интерактивный ввод пароля sudo.
2. **Пакеты идемпотентно**: скрипт должен безопасно повторяться
   (как `apt-get install -y ...`) и не полагаться на прошлое состояние
   файлов на хосте.
3. **Ubuntu 26.04 = codename «resolute»**: VERSION_CODENAME снимается
   с хоста через `/etc/os-release`, в шаблонах используется плейсхолдер
   `{codename}`. Не захардкоживать «resolute» в установку.
4. **Ненадёжные репозитории**: любой неудачно записанный
   `sources.list.d/*.list` ломает весь `apt-get update`. Поэтому в начале
   скрипта явно `rm -f` испорченный docker-листинг; ключ пишется
   деарморированным (`gpg --dearmor`) в `/etc/apt/keyrings/docker.gpg`
   (сырой арм-ключ apt игнорирует как «unsupported filetype»). Ключ
   и листинг пересоздаются каждым запуском — не полагаться на прошлое
   состояние файлов.
5. **Расширение «новыми установками»** — заводить отдельный bash-шаблон
   в `installer.py` и вызывать в `install()` до/после `PKG_INSTALL`,
   не превращая в один гигантский нечитаемый скрипт.
6. **Файлы конфигурации** — в репозитории лежат примеры `config.toml`
   и `HISTORY.md`. Не создавать лишних файлов без нужды.
7. **История изменений** — ведётся в `HISTORY.md` (Changelog, reverse
   chronological). Правки в коммиты не пушатся без явной просьбы
   пользователя.
8. **Портал и сайты Caddy**: каждый сайт — отдельный файл
   `/opt/caddy/sites/*.caddy`, корневой Caddyfile только импортирует их
   (`import /etc/caddy/sites/*.caddy` — контейнерный путь!). В портале всё
   внутри `handle`-блоков, catch-all со `file_server` — последним: иначе
   Caddy отсортирует директивы по-своему и статика перехватит прокси.
